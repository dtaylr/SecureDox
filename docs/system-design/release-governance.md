# Release Governance

Release governance turns engineering evidence into a decision that is visible,
repeatable, and auditable.

## Decision Flow

1. CI runs test, security, and scan jobs.
2. Jobs publish evidence artifacts under `reports/`, `tests/reports/`, and
   `security/sbom/`.
3. `scripts/release-readiness.ts` reads those artifacts.
4. The script emits `reports/release-readiness.json`.
5. A `NO-GO` exits non-zero and blocks the release workflow.

## Ownership

| Area | Owner | Evidence |
| --- | --- | --- |
| Quality | QA/SDET | JUnit, Playwright, flake summary |
| Security | AppSec/DevSecOps | Gitleaks, Semgrep, Trivy, SBOM |
| Reliability | Platform/SRE | Performance summary, error-rate summary |
| Data integrity | Backend/DB | DB smoke tests, audit validation |
| AI-generated tests | QA lead | Generated-test review manifest |

## Governance Rules

- Required evidence must be generated by CI, not hand-edited.
- Missing P0 evidence is a blocker.
- Release exceptions require an issue link, owner, and expiry.
- Audit trail and tenant isolation failures cannot be waived for production.
- Security and data integrity blockers override schedule pressure.

## Artifacts

The release summary artifact is:

```text
reports/release-readiness.json
```

It is uploaded by `.github/workflows/release-gates.yml`.
